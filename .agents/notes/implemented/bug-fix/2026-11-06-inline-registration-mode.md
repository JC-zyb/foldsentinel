# Agent Note: 行内直接更改登记方式

Status: implemented

## Problem

紧凑保护列表同时呈现登记方式摘要和“调整”后的方式表单，修改需要重复进入与应用。名称展开箭头位于名称列末端，靠近登记方式时又像失效的下拉入口。用户明确要求只保留一个登记方式并直接更改。

## Decision

已登记项目在 `.root-policy` 中只使用一个原生 `select`；`change` 先通过 `onPendingMode` 按记录 ID 保留选择，再调用 `apply` 进入现有 `changeProtection` 流程。“调整/收起”、静态重复摘要、二次应用按钮及共用编辑器展开状态退出该入口。不可编辑的记录仍显示静态方式；混合方式须先选择具体值。

成功操作清理待应用方式，失败保留所选值并在原行报告；busy/stale 禁用变更。操作与刷新结果分离、核验、解除及权限冲突确认继续沿用既有流程。异步重绘后的焦点优先恢复原控件，原控件不可见时回退行内方式或可用按钮。

备注保留独立入口和按 ID 保存的展开状态。Escape 只收起并返回备注入口，草稿继续保留；取消清草稿，恢复成功或导入替换记录时清理对应状态。名称箭头贴近文件名，并说明展开用途。

本篇部分替代[桌面工作区布局](2026-10-31-ui-workspace.md)的“摘要 + 调整面板”，以及[文件保护工作区](../feature/2026-10-27-protection-workflow.md)中已登记项目先选后应用的入口；两篇其余布局、隐私、快照及核验理由仍成立。按登记方式、紧凑列表及待应用状态检索活跃笔记后，[最外层名称列表](../feature/2026-10-27-private-recovery-list.md)仅共用展示元数据，本次不改变其隐私边界；没有命中的相关 proposed/rejected 决定，也没有完全吸收的笔记。

## Alternatives considered

- 保留摘要与按需“调整”可压低常驻表单密度，但重复入口令用户难以发现真正可修改的位置，且不符合本次直接更改要求。
- 将方式选择框常驻、仍保留“应用更改”可分开选择与执行，但每行继续需要二次操作；采用原生选择框的明确变更事件提交，并保留失败反馈与操作期间禁用。

## Verification

验证入口为 `npm run build`、`npm test` 及现有多文件、布局和主题浏览器脚本。专项检查唯一可见选择框、一次 change 先保存选择再调用一次 apply、浏览器拒绝原生操作时保留选择、备注 Escape 与重绘状态、busy/stale 禁用，以及中英文代表宽度下选中方式完整可读。本次执行结果及报告见 [UI 审核](../../../../docs/UI_REVIEW.md)的 2026-11-06 记录；旧“调整”方案的通过数量不计入本次结果。

## Consequences

每行只保留一个方式入口，选择即执行，备注编辑不再依赖方式面板。代价是方式变化直接产生执行意图，列表也不再单独提供相同方式的重新应用按钮；添加区仍使用显式应用。失败选择与实际登记记录可能不同，须结合未应用标记和行内错误读取状态。浏览器验证只能证明界面事件和状态边界，不能代替原生 IPC、真实文件权限或 Windows DPI 验收。
